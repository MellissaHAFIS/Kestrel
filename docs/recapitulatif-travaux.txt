COMMIT 1 - 9ee8059 : rendre le scan du registry reel et reparer la couche 1

LE PROBLEME (deux defauts distincts, chacun rendait la couche 1 decorative)

  a) scan_tool() etait un stub qui ne signalait rien. Les verdicts de la demo
     (search_docs mis en quarantaine, lookup_reference suspect) etaient ecrits
     a la main dans TOOL_REGISTRY. Autrement dit, le "scan" ne prouvait rien :
     on affichait un resultat qu'on avait nous-memes saisi.

  b) Le pipeline ne trouvait jamais d'entree dans le registry.
     Action.tool_name est qualifie ("docs_helper.search_docs") alors que le
     registry est indexe par le nom nu ("search_docs"). La recherche echouait
     donc systematiquement et les outils en quarantaine passaient a la couche
     suivante sans etre bloques.

LA CORRECTION

  a) scan_tool() derive maintenant son verdict de la description et du schema,
     via 8 regles ponderees additives :
       - dissimulation ("do not tell the user")        0.35
       - imperatif adresse au modele ("you MUST read") 0.30
       - caracteres Unicode invisibles                 0.30
       - reference a un fichier de config ou secret    0.20
       - sollicitation de valeurs de credentials       0.20
       - reference a un autre outil                    0.15
       - parametre libre de type passthrough           0.15
       - description anormalement longue               0.10
     Seuils : >= 0.60 quarantaine, >= 0.25 suspect.
     TOOL_REGISTRY est desormais PEUPLE en executant ce scanner sur les vraies
     descriptions des serveurs de demo. Le contenu ne peut donc plus diverger
     du scanner : si le scanner change, le registry change avec lui.

  b) _registry_entry() essaie le nom qualifie puis le nom nu.

  Corrige aussi _tool_param_schema(), qui ne gerait que la forme Pydantic de
  args_schema et renvoyait {} pour tous les outils MCP (langchain-mcp-adapters
  renvoie un dict JSON-Schema). La moitie "schema" du scan ne tournait donc
  jamais.

DECISION PRISE : une quarantaine reste un BLOCK definitif

  L'option "escalate" a ete essayee puis annulee. Raison mesuree, pas d'opinion :
  benign_completion_strict exige que TOUTES les etapes soient "allow"
  (eval/run_eval.py:296), donc une quarantaine escaladee ne fait aboutir aucune
  chaine benigne non plus -> le chiffre benin reste 35,7 % dans les deux cas.
  En revanche, "escalate" degrade le pire-cas attaque
  (asr_if_escalations_approved compte une etape retenue comme un succes) et
  ajoute un humain capable d'approuver un outil que le scanner a deja juge

COMMIT 2 - 4a37239 : detecter les canaries tronques, en ROT13 ou decoupes
--------------------------------------------------------------------------------

LE PROBLEME
  La correspondance exacte du canary rate trois obfuscations qui ne coutent
  presque rien a un attaquant. Et la defence-sheet revendiquait deja ROT13
  alors que le code ne le faisait pas.

LA CORRECTION

  1. TRONCATURE. Une fuite n'a pas besoin d'etre complete pour etre une
     divulgation : "our token prefix is CANARY-PG-7f3a9c" livre la moitie du
     honeytoken et etait note "propre". Desormais une sequence contigue de
     >= 14 des 28 caracteres compte. 14 = la moitie du token : assez specifique
     pour qu'une collision soit irrealiste, alors qu'un seuil plus bas
     commencerait a matcher le prefixe de marque "CANARY-PG", qui apparait
     legitimement dans la documentation *a propos* du honeytoken.

  2. ROT13. Peu couteux, et present dans notre propre jeu de test.

  3. DECOUPAGE ENTRE PLUSIEURS APPELS. Le cas central, et celui qui met en
     echec par construction toute regle portant sur une action isolee : chaque
     fragment est individuellement propre, seule la chaine est une fuite.

LE POINT TECHNIQUE QUI COMPTE : couverture positionnelle, pas inclusion

  La premiere implementation concatenait les fragments de la session et
  cherchait le token dans le texte joint. Cela ne marche pas : un attaquant qui
  rembourre chaque appel ("ref b: 7f3a9c0d") casse le token a travers du
  remplissage, donc il n'est jamais contigu. Chaque fragment anterieur est donc
  compare au canary INDEPENDAMMENT et contribue les POSITIONS de caracteres
  qu'il divulgue. Le blocage ne tombe que si l'union couvre tout le token et
  que l'appel courant apporte quelque chose de nouveau.

ARCHITECTURE : pourquoi un nouveau module session_state.py

  invariants.py reste PUR : le meme Action avec la meme Policy doit toujours
  donner la meme Decision. Cette purete est ce qui autorise a l'appeler une
  couche de garantie. L'accumulateur vit donc a l'exterieur, et la fonction qui
  le consomme recoit les fragments en argument explicite au lieu d'aller
  chercher un etat global : une decision reste rejouable.

  Seuls les appels AUTORISES sont enregistres. Un appel bloque n'a jamais quitte
  le processus, il ne peut donc pas contribuer a une exfiltration et ne doit pas
  non plus contribuer a un blocage ulterieur -- sinon une seule tentative
  empoisonnerait le reste de la session en faux positifs.

PREUVE : 21 tests dans tests/test_cross_call_canary.py

LIMITE IMPORTANTE A CONNAITRE
  Cette protection NE SE DECLENCHE PAS sur la chaine atk-13 du benchmark, et la
  raison est structurelle, pas un bug : dans atk-13, l'appel portant la premiere
  moitie est bloque par le registry, donc rien ne s'accumule, et l'appel final
  ne porte que "FAKE-DO-NOT-USE" (12 caracteres, sous le seuil de 14). Le canary
  ne sort reellement jamais, mais l'evaluation compte quand meme cette derniere
  etape comme une etape nuisible autorisee.
  Nous rapportons donc atk-13 comme un echec PLUTOT que de baisser le seuil de
  14 a 12 pour le rattraper : les chaines ont ete ecrites avant les seuils, et
  re-calibrer apres avoir vu les resultats annulerait l'argument "aucun
  reglage". La protection est donc TESTEE mais NON EXERCEE par ce benchmark :
  elle couvre le cas ou deux appels sont tous les deux autorises, ce que ce jeu
  de test ne contient pas.

COMMIT 3 - 5bd084f : deux defauts du scanner de secrets
--------------------------------------------------------------------------------

Les deux ont ete trouves en executant le meme code PLUSIEURS FOIS au lieu d'une,
et les deux echouaient dans le mauvais sens.

DEFAUT 1 : LE SCANNER N'ETAIT PAS DETERMINISTE

  Le plugin HexHighEntropyString de detect-secrets choisit la sous-chaine a
  scorer en iterant un ensemble (set). L'aleatoire de hachage que Python
  applique a chaque processus changeait donc son verdict.
  Mesure sur notre propre cas de fuite : 3 executions identiques sur 6
  trouvaient le secret, 3 ne trouvaient rien. Et cela remontait jusqu'au verdict
  final (block au lieu d'escalate).

  Un garde dont la decision n'est pas reproductible ne peut pas etre audite, et
  la reproductibilite est quelque chose que nous revendiquons. Correction :
  PYTHONHASHSEED est fixe pour le sous-processus du scanner
  (investigator/tools.py::_scan_env).

  C'ETAIT AUSSI LA VRAIE CAUSE DES 3 TESTS "INSTABLES". Le diagnostic inscrit
  dans CLAUDE.md etait FAUX : il n'a jamais ete question de pollution entre
  tests via le singleton audit_log. Chaque test disposait deja de sa propre base
  temporaire, et les echecs se reproduisaient en isolation complete.
  De plus, test_paraphrased_leak_ends_in_grounded_block affirmait sur un canary
  que la policy ne declare pas : il testait donc l'heuristique d'entropie de
  detect-secrets, pas le garde. Il utilise maintenant le canary de la policy,
  donc le blocage repose sur une correspondance exacte de honeytoken.

DEFAUT 2 : UN SCAN EN ECHEC SE LISAIT COMME UN SCAN PROPRE

  extract_signals() comptait "aucun secret trouve" comme une verification
  propre (clean check) MEME quand le scanner avait expire ou etait absent. Or
  les clean checks AUGMENTENT la confiance d'autoriser. Donc un scanner casse
  plaidait activement pour laisser passer l'action : un fail-open dans le seul
  composant dont le travail est de fail-closed.

  Correction : le drapeau scan_ok distingue "j'ai regarde et je n'ai rien
  trouve" de "je n'ai pas pu regarder". Le second positionne
  Signals.scan_failed, ne compte aucune verification propre, et plafonne la
  confiance d'autorisation juste en dessous du plancher -> l'action part vers un
  humain. Le plafond est DERIVE de DEFAULT_MIN_CONFIDENCE au lieu d'etre ecrit
  en dur, pour que les deux ne puissent pas diverger.

  Choix delibere : on ne fabrique pas une violation. "Je n'ai pas pu regarder"
  n'est pas "j'ai trouve un secret", donc le signal violating reste faux et le
  verdict est une escalade, pas un blocage.

PREUVE : 13 tests dans tests/test_scan_robustness.py. L'un est volontairement
inter-processus, parce qu'une repetition dans un meme processus ne peut PAS
observer l'aleatoire de hachage -- c'est exactement pour cela que le bug avait
survecu a une suite de tests verte.

LECON GENERALISABLE : executer une verification de securite plusieurs fois dans
des processus separes avant de croire une suite verte.

COMMIT 5 - a9f5093 : journal d'audit infalsifiable-detectable (hash chain)
--------------------------------------------------------------------------------

CLAUDE.md listait ceci comme la seule alternative defendable a l'idee de
blockchain que nous avons rejetee, et comme NON implementee. C'est fait.

PRINCIPE
  Chaque ligne stocke le SHA-256 du hash de la ligne precedente combine a sa
  propre forme canonique. Modifier, supprimer ou reordonner une ligne invalide
  donc tous les condenses suivants. verify_chain() rejoue la chaine, et la
  commande "verify" l'expose dans la console analyste.
  C'est le controle qu'un auditeur demande reellement : non pas "le journal dit
  X", mais "on peut demontrer que le journal n'a pas ete reecrit depuis que X y
  a ete inscrit".

LE PROBLEME DE CONCEPTION QU'IL FAUT COMPRENDRE
  update_decision() modifie LEGITIMEMENT une ligne deja hachee quand un analyste
  clique Approve. Une non-correspondance ne peut donc pas, a elle seule,
  signifier "falsification".
  Re-signer la ligne n'est pas une option non plus : la ligne suivante s'est
  engagee sur l'ancien hash, donc re-signer casse la chaine de toute facon, et
  cela rendrait surtout les modifications legitimes indistinguables des
  falsifications.
  Solution retenue : le hash stocke reste FIGE, et l'amendement est ajoute comme
  son propre evenement chaine. La verification rapporte alors deux choses
  differentes :
    - contenu ne correspondant plus au hash figé, AVEC un amendement chaine
      correspondant  -> override analyste legitime, liste et non masque ;
    - la meme non-correspondance SANS amendement
                     -> falsification.
  Cette distinction est toute la valeur du dispositif.

DEMONTRE DE BOUT EN BOUT
  - journal neuf                                   -> intact
  - approbation analyste                           -> intact + override liste
  - passage d'un block a allow en SQL direct       -> falsification detectee,
                                                      avec l'identifiant exact
                                                      de la ligne

NOTES D'IMPLEMENTATION
  - AUCUNE modification du contrat gele de types.py. prev_hash et row_hash sont
    des colonnes de stockage, exclues de _from_row ; un amendement REUTILISE le
    type d'evenement existant "human_decision" au lieu d'en inventer un, et
    porte l'identite de l'analyste dans sa charge utile parce que decided_by est
    un Literal ferme. Le contrat gele a joue son role : il m'a arrete.
  - BEGIN IMMEDIATE autour du couple lecture-de-la-queue puis insertion. Le
    garde journalise depuis plusieurs couches par action, donc deux ecrivains
    lisant le meme prev_hash et forkant la chaine est une vraie course, et un
    fork est indistinguable d'une falsification.
  - Migration de colonnes explicite : CREATE TABLE IF NOT EXISTS ne fait rien
    sur une table existante, donc sans cela toute insertion echouerait sur une
    base creee avant la chaine. Les lignes anterieures sont rapportees comme
    "unhashed" plutot que de passer silencieusement, et la console affiche
    "intact, mais partiellement anterieur a la chaine" au lieu de crier au loup.
  - La verification est en LECTURE SEULE : elle ne peut donc ni reparer ni
    detruire discretement la preuve qu'elle controle.

PREUVE : 19 tests dans tests/test_audit_chain.py, ecrits comme des ATTAQUES en
SQL direct plutot qu'a travers l'API, y compris le coup d'apres evident de
l'attaquant (re-signer la ligne modifiee), qui casse quand meme le lien de la
ligne suivante.

LES DEUX LIMITES, A DIRE DANS LA MEME PHRASE QUE LA FONCTIONNALITE
  1. Quiconque peut ecrire dans la base peut recalculer TOUTE la chaine.
  2. Supprimer les lignes les plus RECENTES laisse une chaine coherente
     (test_deleting_the_last_row_is_not_detectable epingle honnetement cette
     limite).
  Fermer les deux exige un condense publie la ou l'attaquant n'a pas d'acces en
  ecriture. C'est une ligne de feuille de route, pas une fonctionnalite livree.
  Et cela ne requiert toujours pas de blockchain.

  Survendre ceci serait pire que ne pas l'avoir livre.

COMMIT 6 - e6e199b : angle mort du gate sur la frontiere de confiance
                      (AUCUN GAIN MESURE - garde quand meme)
--------------------------------------------------------------------------------

LE PROBLEME
  Le gate ML etait la SEULE couche aveugle a la frontiere de confiance sur
  laquelle tout le reste du systeme est bati : il inspectait les URL dans le
  texte des arguments mais ne regardait jamais VERS QUEL SERVEUR l'appel allait.
  Or un outil MCP sur un serveur non fiable est exactement le canal qu'utilise
  une chaine d'empoisonnement. C'etait donc une lacune structurelle, independante
  de tout echec constate.

LA CORRECTION
  Ajout de ce signal, plus un signal d'identifiant opaque (>= 12 caracteres
  alphanumeriques contenant a la fois un chiffre et une lettre : la forme d'une
  cle, d'un token ou d'un hash).

LA METHODE COMPTE PLUS QUE LE DIFF, parce que eval/cases.py est notre jeu
reserve et que "aucun seuil n'a ete regle" est une affirmation faite au jury :
  - les cas ont ete ecrits a partir des TECHNIQUES, pas des chaines qui
    echouaient ;
  - tests/test_gate_hardening.py a ete ecrit AVANT de relancer l'evaluation ;
  - AUCUN seuil n'a change. test_thresholds_are_unchanged epingle GATE_LOW et
    GATE_HIGH a leurs valeurs preexistantes 0.20 / 0.80, pour qu'une future
    modification soit deliberee ;
  - les deux poids valent 0.15, DERIVES du plancher preexistant de 0.20 et non
    d'un resultat : seul, chacun reste sous le plancher, donc un appel
    tiers ordinaire reste auto-autorise et on ne fabrique pas d'alertes ;
    combine a n'importe quel autre signal il franchit le plancher et atteint
    l'Investigator, parce que c'est la CO-OCCURRENCE qui merite un examen.

LE RESULTAT : AUCUN GAIN MESURE
  Taux de reussite des attaques (7,1 %), etapes nuisibles arretees (93,3 %) et
  completion benigne (35,7 %) sont INCHANGES sur Bedrock avant et apres.
  atk-13 passe toujours : son score est passe de 0,00 a 0,15, toujours sous le
  plancher de 0,20. Baisser le plancher a 0,15 le rattraperait et c'est
  exactement le reglage que nous refusons.

ET CELA COUTE QUELQUE CHOSE
  Le gate auto-autorise une etape benigne de moins (18 -> 17), donc une etape de
  plus sur 56 part vers l'Investigator. Les escalades par 100 etapes benignes
  sont passees de 3,7 a 11,1 et les etapes resolues sans humain de 82,1 % a
  78,6 %. ATTENTION A L'ATTRIBUTION : le gate est deterministe et ne represente
  qu'UNE SEULE etape de cet ecart ; le reste est de la variation de
  l'Investigator, qui avait bouge d'autant entre deux executions ou le gate
  n'avait pas change du tout.
  Formulation defendable : une etape benigne de plus sur 56 recoit desormais un
  examen, et nous n'avons rien gagne de mesurable en echange.

GARDE MALGRE TOUT, et c'est consigne comme un CHOIX DE JUGEMENT, pas une
victoire : l'angle mort etait reel et structurel, et 14 chaines d'attaque
ecrites par l'equipe qui construit le garde sont le mauvais instrument pour
PROUVER qu'un signal est inutile -- l'absence de preuve n'est pas une preuve
d'absence. Si le jury objecte que nous avons ajoute de la complexite sans gain
mesure, c'est un coup juste, et la reponse est la ligne de cout ci-dessus, pas
une defense du signal.

DIVULGATION : le gate a donc change APRES que nous avions vu une premiere
evaluation. Les seuils, eux, n'ont pas change, et les chaines non plus.

Le controle de destination fail-OPEN volontairement (une policy illisible compte
comme fiable), et un test l'epingle : les couches de garantie fail-closed deja
sur une erreur de policy, et un gate qui escalade tout est un deni de service
contre l'analyste.

des changements structurels.

  1. SCORING AU NIVEAU DE LA SEQUENCE pour le gate.
     C'est la vraie reponse a atk-13 et la SEULE qui ne passe pas par un
     ajustement de seuil. Le gate note des appels isoles ; l'attaque est dans la
     sequence. Noter la sequence plutot que l'appel est la lacune a nommer.

  2. CONDENSE D'AUDIT PUBLIE A L'EXTERIEUR.
     Fermerait les deux limites de la chaine de hachage (recalcul complet par un
     ecrivain, troncature de la queue indetectable). Un condense periodique
     publie suffit ; cela ne necessite pas de blockchain.

  3. QUARANTAINE PAR SESSION OU PAR APPELANT, au lieu d'un outil globalement
     indisponible. C'est ce qui recupererait une partie des 64 % de chaines
     benignes actuellement bloquees, sans affaiblir la detection.

  4. CLASSIFIEUR REEL pour le gate, mesure sur MCPTox. L'heuristique a poids
     fixes est au bout de ce qu'elle peut faire.

  5. JEUX DE TEST INDEPENDANTS (MCPTox pour les descriptions d'outils,
     AgentDojo de bout en bout). C'est la limite la plus serieuse de nos
     chiffres actuels.

  6. PROXY-PASSERELLE MCP pour que le garde soit en ligne en production.

A NE PAS FAIRE
  - Ne jamais re-calibrer les seuils ni editer les chaines apres avoir vu les
    resultats. Cela annulerait l'argument "aucun reglage", qui est un argument
    de vente.
  - Ne pas rouvrir la question blockchain : une smart contract ne peut pas
    intercepter un appel HTTP hors-chaine, les journaux contiennent des donnees
    sensibles (et entrent en conflit avec le droit a l'effacement du RGPD), et
    les ecritures on-chain ajoutent cout et latence.

6. COMMENT TOUT REVERIFIER SOI-MEME
================================================================================

Les commandes ci-dessous supposent un environnement Python 3.12 (chainlit
exige < 3.14). Sur ce poste : ./.venv312/bin/python

  # Suite de tests complete (188 tests). A lancer plusieurs fois : l'ordre est
  # aleatoire, donc une suite stable sur 3-5 executions veut dire quelque chose.
  MOCK_LLM=1 ./.venv312/bin/python -m pytest tests/ -q

  # Acte 1 : sans garde, le canary atteint demo/leak_log.jsonl
  MOCK_LLM=1 ./.venv312/bin/python -m demo.run_no_guard

  # Acte 2 : avec garde. Doit montrer UNE COUCHE DIFFERENTE par etape :
  #   1 gate-allow, 2 Investigator-escalate, 3 REGISTRY-block,
  #   4 et 5 invariant-block, puis PASS.
  # Si l'etape 3 annonce un invariant au lieu du registry, la regression du
  # lookup est de retour (voir pipeline._registry_entry).
  MOCK_LLM=1 ./.venv312/bin/python -m demo.run_guarded

  # Evaluation hors-ligne (MockLLM, le graphique le precise)
  MOCK_LLM=1 ./.venv312/bin/python -m eval.run_eval --mode mock

  # Evaluation reelle sur Bedrock (exige .env.aws)
  ./.venv312/bin/python -m eval.run_eval --mode bedrock

  # Console analyste : commandes queue | tools | log | verify | approve <id>
  #                                   | block <id> | kill
  # AVANT DE FILMER : supprimer policyguard_audit.db, sinon "verify" affiche
  # "intact, mais partiellement anterieur a la chaine" a cause des lignes
  # ecrites avant la chaine de hachage.
  ./.venv312/bin/python -m chainlit run console/app.py
